# Yandex Search Guard

Сервис проверки поисковых запросов Open WebUI перед отправкой в Yandex Search API. Объединяет настраиваемые правила, локальный LLM-классификатор и веб-панель для управления политикой и просмотра решений.

## Назначение

Шлюз позволяет централизованно определять, какие поисковые строки можно отправлять во внешний поиск. Офицер ИБ настраивает категории и словари, администратор подключает сервис к OWUI и модели. При недоступности классификатора поиск приостанавливается до восстановления проверки.

## Архитектура

```text
Open WebUI (engine=yandex)
    | поисковая строка + SEARCH_TOKEN
    v
Search Guard
    |-- нормализация и правила
    |-- локальный LLM-классификатор
    |       BLOCK / ошибка -> ответ без вызова Яндекса
    |       ALLOW -> подготовка параметров -> Yandex Search API
    |                                            |
    |<--------------- JSON с rawData -------------+
    |-- журнал решений в SQLite
    +-> ответ Open WebUI

Браузер администратора -> HTTPS / reverse proxy -> веб-панель
```

Проверяется query.queryText. История чата автоматически не передаётся классификатору шлюза. Правила выполняются до модели: credentials, распространённые форматы ключей, email, телефоны/длинные номера, непубличные IP, внутренние домены и запрещённые подстроки. Проверки email/телефонов/IP переключаются отдельно.

Модель оценивает строку по системной политике. Принимается JSON с единственным полем decision=ALLOW/BLOCK и завершением finish_reason=stop. Ошибка или неполный ответ не разрешают отправку. JSON mode — настройка совместимости, строгая проверка ответа сохраняется и без него.

Для Яндекса запрос собирается из разрешённых полей; входные заголовки и произвольные метаданные не пересылаются. searchType и region задаются на сервере. folderId необязателен; при заполнении передаётся серверное значение длиной до 50 символов. Endpoint провайдера зафиксирован в коде. Выдачу rawData декодирует OWUI.

## Запуск

```bash
python3 init.py
docker compose -p yandex-search-guard up -d --build
curl -fsS http://127.0.0.1:8091/healthz
```

init.py создаёт .env с отдельными ADMIN_PASSWORD и SEARCH_TOKEN, сохраняя существующий файл. Панель по умолчанию доступна на http://127.0.0.1:8091. Для сетевого доступа используйте существующий reverse proxy с HTTPS и авторизацией панели. Способ размещения выбирается в рамках принятой инфраструктуры веб-приложений.

Для панели под /search-guard/ reverse proxy удаляет префикс перед передачей в FastAPI, сохраняет Authorization и перенаправляет /search-guard на /search-guard/. Фронтенд использует относительные URL. Кеширование панели и API отключается. Настройки Compose в этой документационной редакции не меняются.

### Варианты сборки

- Dockerfile — установка из доступного pip-индекса.
- Dockerfile.offline — установка из локального wheelhouse с --no-index. Нужны все зависимости под Python 3.12 и архитектуру Linux-контейнера, а также доступный базовый образ.

```bash
docker build -f Dockerfile.offline -t yandex-search-guard:offline .
```

Для офлайн-сборки через Compose задайте build.dockerfile: Dockerfile.offline в локальном override. Во всех командах используйте одинаковый набор -f. Wheelhouse и веса моделей поставляются отдельно. Верхнеуровневые pins не фиксируют все транзитивные зависимости.

## Настройки модели и ключей

В панели задайте API base без /chat/completions, ID локальной instruction-модели, ключ при необходимости, timeout и JSON mode. Пример для Ollama в общей Docker-сети: http://ollama:11434/v1. При обращении через хост указывается опубликованный порт хоста.

Выбранный backend и его маршруты должны соответствовать принятой схеме обработки данных; для локальной классификации используется маршрут без внешнего fallback.

| Параметр | Назначение |
|---|---|
| ADMIN_PASSWORD | Вход в панель |
| SEARCH_TOKEN | Подключение OWUI к шлюзу |
| Yandex API key | Обращение шлюза к Яндексу |
| Ключ API модели | Доступ к классификатору при необходимости |

В OWUI указывается SEARCH_TOKEN, не настоящий ключ Яндекса. Сохранённые ключи не возвращаются через admin API; пустое поле сохраняет прежнее значение. Ключи хранятся в SQLite без прикладного шифрования. Для volume, .env и резервных копий применяется обычный порядок защиты сервисных данных; в публичный Git они не включаются.

## Подключение Open WebUI

Обеспечьте сетевую связность OWUI и шлюза. Для контейнеров можно использовать общую Docker-сеть, закреплённую в Compose. Примеры: compose.network.yaml и owui.compose.example.yaml; второй файл — фрагмент настройки существующего OWUI, не отдельный stack.

```yaml
ENABLE_WEB_SEARCH: "True"
WEB_SEARCH_ENGINE: "yandex"
YANDEX_WEB_SEARCH_URL: "http://search-guard:8000/v2/web/search"
YANDEX_WEB_SEARCH_API_KEY: "<SEARCH_TOKEN>"
YANDEX_WEB_SEARCH_CONFIG: '{"query":{"searchType":"SEARCH_TYPE_RU"}}'
```

Проверьте фактические параметры в Admin Settings OWUI: сохранённая конфигурация может иметь приоритет над environment. Для машинного поиска допускается прямое обращение по Docker-сети. Шлюз принимает Api-Key/Bearer с SEARCH_TOKEN.

## Журнал решений

Панель показывает последние 200 подходящих событий. Доступны фильтры ALL/BLOCK/ALLOW/ERROR и поля: время, request_id, источник test/yandex, решение, код, длительность.

Хранение текста управляется независимо через log_blocked_queries и log_allow_queries. По умолчанию оба выключены. При включении сохраняется до 4096 символов исходного текста; для ERROR текст не записывается. Выключение прекращает новую запись, не удаляя прежнюю.

События старше 30 дней удаляются при старте, каждый час и при операциях журнала. Дополнительно сохраняется не более 10 000 строк, поэтому при высокой активности история короче 30 дней. Если сервис остановлен, очистка возобновляется при запуске. Резервные копии обслуживаются отдельно. SQLite использует освободившиеся страницы повторно; уменьшение файла и обслуживание VACUUM выполняются отдельно при необходимости. Удаление строк не является физическим стиранием копий данных.

Журнал предназначен для оперативного разбора решений. Он не содержит пользователя OWUI и полного аудита административных действий; часть ранних HTTP-отказов в него не входит. Администратор может очистить журнал. Запись события после внешнего вызова не образует с ним единую транзакцию.

## Диагностика

| Код / признак | Значение |
|---|---|
| /healthz | Процесс отвечает; проверка модели и поиска выполняется отдельно |
| MODEL_ALLOW, origin=test | Проверка строки без вызова Яндекса |
| FORWARDED, origin=yandex | Получен ожидаемый HTTP JSON-ответ провайдера с rawData |
| EMAIL/CREDENTIAL/INTERNAL_DOMAIN и т.п. | Сработало правило |
| MODEL_BLOCK | Модель отклонила строку по политике |
| MODEL_ERROR/MODEL_INCOMPLETE | Проверка моделью не завершена корректно |
| YANDEX_ERROR | Ошибка обращения к поисковому API |
| HTTP 401 / 403 / 422 | Аутентификация / блокировка / параметры запроса |
| HTTP 503, BUSY | Не получен слот обработки |

Лимиты: строка 4096 символов, POST 64 KiB, 4 задачи, ожидание слота до 2 секунд, один worker. Получение найденных страниц выполняется OWUI отдельно от поискового запроса.

## Проверка и сопровождение

```bash
docker compose -p yandex-search-guard run --rm --no-deps -v "$PWD/tests:/app/tests:ro" search-guard python -m unittest discover -s tests -v
```

При дополнительных compose-файлах используйте тот же набор -f. При настройке проверьте обычный поиск, выбранные категории BLOCK, недоступность модели и параметры журнала на синтетических примерах.

Для опубликованного экспорта проверены совпадение файлов по хешам, синтаксис Python и отдельные функции SQLite: folderId, флаги текстов, 4096 символов, 30 дней и 10 000 строк. Полная FastAPI-интеграция, миграция, расписание lifespan, Docker build и live-вызовы в среде подготовки не запускались. Старый VALIDATION.json относится к прежнему набору проверок.

## Область применения

Сервис контролирует маршрут Yandex Search через настроенный URL. Основная LLM, другие инструменты и загрузка страниц настраиваются отдельно. Правила и классификатор адаптируются к рабочим примерам: возможны пропуски и ложные блокировки. Панель использует единую административную учётную запись; SSO/RBAC и ограничение частоты обращений при необходимости организуются средствами инфраструктуры.

[Инструкция для офицера ИБ](docs/SECURITY_OFFICER.md) описывает настройку политики, просмотр решений и сопровождение.
