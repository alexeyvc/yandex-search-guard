# Инструкция для офицера информационной безопасности

## Для чего используется сервис

Yandex Search Guard помогает применять единую политику к поисковым строкам Open WebUI. До отправки в Яндекс строка проходит правила и локальную модель. В панели доступны настройка категорий, словарей и просмотр результатов проверки.

Основной рабочий цикл: настроить политику, проверить типовые примеры, просматривать решения и корректировать правила по результатам эксплуатации.

## Как проходит запрос

1. OWUI отправляет поисковую строку в шлюз с сервисным токеном.
2. Шлюз нормализует текст и применяет правила.
3. Если правила не сработали, локальная модель оценивает строку по системной политике.
4. При ALLOW строка направляется в Yandex Search API. При BLOCK внешний поиск не выполняется.
5. Если классификатор не смог завершить проверку, поиск приостанавливается для этого запроса.
6. Решение отражается в журнале, если обработка дошла до записи события.

Яндекс получает разрешённую нормализованную строку. История чата автоматически не передаётся классификатору шлюза. Основная модель и остальные инструменты OWUI работают по собственной конфигурации.

## Доступ и организация работы

Работа выполняется через веб-панель по HTTPS с административной авторизацией. Для публикации используется принятый в организации способ размещения веб-приложений.

Технический администратор подключает OWUI, модель и ключ Яндекса. Ответственный за политику определяет категории и словари, проверяет примеры и разбирает результаты. В приложении используется единая административная учётная запись; организационные роли и согласование изменений ведутся в обычном порядке вне приложения.

Пароль панели, токен OWUI и ключи провайдеров имеют разные назначения. Настоящий ключ Яндекса размещается в шлюзе; OWUI использует только SEARCH_TOKEN. Параметры reverse proxy и подключения приведены в README.

## Первичная настройка политики

Согласуйте перечень сведений, которые не должны попадать во внешний поиск, и допустимые публичные запросы. Затем настройте:

- проверки email, телефонов/длинных номеров и непубличных IP;
- внутренние домены и запрещённые подстроки;
- системную политику локального классификатора;
- необходимость сохранения текстов ALLOW и BLOCK.

Правила credentials и распространённых форматов ключей действуют независимо от переключателей email/телефонов/IP. Словари задаются строками, без регулярных выражений. Для воспроизводимости зафиксируйте выбранную модель, её ревизию, параметры и текущую политику в принятом реестре изменений.

## Проверка перед использованием

Используйте синтетические примеры: публичный технический вопрос, тестовый email, вымышленный внутренний домен, условный credential и вымышленный кадровый/медицинский контекст.

| Проверка | Ожидаемый результат |
|---|---|
| Обычный технический запрос | ALLOW при соответствующей политике |
| Категория, запрещённая правилом | BLOCK с кодом правила |
| Контекст, запрещённый политикой модели | MODEL_BLOCK |
| Модель недоступна или ответ некорректен | Поиск не выполняется |
| Поиск через OWUI | Событие origin=yandex; при успехе FORWARDED |
| Переключатели текста | Сохранение только для включённых категорий |

Для подтверждения работы используйте журнал шлюза и результаты тестов, а не только текст ответа чат-модели. При вводе в эксплуатацию администратор дополнительно проверяет миграцию, рестарт, очистку журнала и работу под ожидаемой нагрузкой.

## Просмотр решений

Начните с фильтра BLOCK. При необходимости используйте ERROR, ALLOW или ALL.

- EMAIL, CREDENTIAL, INTERNAL_DOMAIN и другие коды обозначают правило.
- MODEL_BLOCK означает решение классификатора по политике.
- MODEL_ERROR и MODEL_INCOMPLETE обозначают технический результат проверки, а не категорию данных.
- MODEL_ALLOW с origin=test относится к проверке в панели без обращения к Яндексу.
- FORWARDED с origin=yandex означает получение ожидаемого HTTP JSON-ответа поискового API.
- YANDEX_ERROR относится к обращению к провайдеру и разбирается администратором.

При избыточной блокировке уточните правило или политику, добавьте пример в проверочный набор и повторите тест. BLOCK сам по себе не характеризует намерения пользователя; ALLOW означает результат проверки, а не формальное подтверждение состава данных.

## Параметры журнала

По умолчанию сохраняются метаданные решений, без текста. Запись исходных строк включается отдельно для BLOCK и ALLOW. Длина записи — до 4096 символов; маскировка текста не выполняется. Для ERROR текст не сохраняется. Выключение переключателя прекращает новые записи текста, сохраняя ранее накопленную историю.

Журнал хранится до 30 дней с дополнительным пределом 10 000 событий. При высокой активности старые строки удаляются раньше. Очистка выполняется при запуске, каждый час и при операциях журнала; после остановки сервиса возобновляется при его запуске. Панель показывает последние 200 событий выбранного фильтра.

Срок и доступ к резервным копиям определяются отдельно. Удаление строк из SQLite не означает физическое стирание содержимого резервных копий и свободных страниц файла. Настройки и ключи также находятся в SQLite, без прикладного шифрования; для БД и копий применяется принятый порядок защиты сервисных данных. Исходные тексты просматриваются уполномоченными сотрудниками и не включаются в публичные обращения.

## Сопровождение

Согласуйте ответственных за политику, доступ к панели, резервное копирование и техническую диагностику. При изменении модели, словарей или системной политики повторяйте проверочный набор. Обновления приложения сопровождаются резервной копией и проверкой совместимости БД при откате.

При нестандартном результате сохраните время, request_id, источник и код, затем передайте информацию ответственному администратору. Если обнаружена нежелательная отправка, временно приостановите поисковый маршрут и разберите случай по принятому регламенту. При подтверждённом раскрытии ключа его заменяют. До очистки журнала сохраняют необходимые сведения для разбора в согласованном месте.

## Особенности учёта

Журнал предназначен для оперативной работы: он не содержит пользователя OWUI, полного аудита действий и версий политики на каждом событии. Некоторые ранние HTTP-отказы не записываются. Администратор может очистить журнал; при необходимости длительного учёта согласованные сведения фиксируются отдельно. Внешний вызов и последующая запись события не образуют единую транзакцию.

Область контроля — поисковые строки по настроенному маршруту Яндекса. Для других инструментов OWUI используется отдельная конфигурация. Качество классификации оценивается на рабочих примерах с учётом возможных пропусков и ложных блокировок. Срок 30 дней — параметр приложения; организационные и нормативные требования к учёту определяются отдельно.
